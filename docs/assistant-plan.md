# 업무도우미 데이터 비서 기획 — 커스텀 리포트를 "무엇이든 묻는" 에이전트로 (2026-10-19)

대표 요청: "커스텀 리포트를 더 개선해보자. 업무도우미 기반으로 어떠한 질문도 데이터화할 수 있다면 답변하는 걸로. 혹은 정성적인 답변도 가능하도록 하는 AI."

## 0. 지금 상태 (코드 기준)

| 항목 | 지금 |
|---|---|
| 방식 | 질문 → AI 가 SQL 한 개 생성(`planReport`) → `run_report`(SELECT 전용·화이트리스트 47개 관계·5,000행) → 표. 오류면 최대 2회 교정 |
| 성격 | '데이터 조회 엔진' — 해석·추정·추천 **금지**(프롬프트 규칙 8). 질문이 "왜?"여도 숫자만 |
| 볼 수 있는 것 | 매출·재고·발주·생산·물류·VOC·마케팅 **표 데이터**. 글(문의 본문·리포트 본문·매뉴얼 본문·요청 메모)은 SQL 로 긁을 수는 있으나 읽고 요약하는 흐름이 없다 |
| 못 보는 것 | 고객 PII(`sales_customers`), 입금 원문(`bank_deposits`), 네이버 문의(`channel_inquiries`), 종합 리포트 본문(`analyst_reports`), 월간 VOC 리포트, OKR 체크인, 계정·토큰 |
| 시간 | 라우트 120초, AI 호출 60초 — 한 번 묻고 한 번 답하는 구조 |
| 부가 | 저장 리포트(변수 치환), 루커스튜디오 SQL, Opus 캐싱 |
| 모델 | 2026-10-19 부터 Fable 5.1 기본 |

종합 리포트(`analyst.ts`)는 이미 **도구 루프**(sku_detail·channel_trend·listing_status·stock_status·메타·네이버 6개, 최대 5회 조사, 270초 기한)를 갖고 있다. 비서는 이 루프를 일반 질문용으로 다시 쓰는 것이다.

## 1. 목표 — 한 문장

"지난달 톡스토어 매출이 왜 빠졌지?"처럼 **숫자와 이유를 같이 묻는 질문**에, 표를 뽑고 글(문의·VOC·리포트·메모)을 읽어 **근거 붙은 답**을 주는 비서. 숫자만 원하면 지금처럼 표만, 이유를 물으면 '사실'과 '추정'을 갈라 쓴다.

## 2. 설계

### 2-1. 질문 유형 셋, 입구는 하나
| 유형 | 예 | 비서가 하는 일 |
|---|---|---|
| 정량 | "10월 채널별 매출", "재고 10일 미만 품목" | SQL 1~3회 → 표 (+ 한 줄 요약). 지금과 같되 여러 번 조회 가능 |
| 정성 | "이번 달 VOC 에서 가장 많은 불만은?", "배송 지연 문의가 늘었나?", "지난주 종합 리포트가 지적한 것" | 글 검색 → 읽기 → 요약·분류, 원문 인용 붙임 |
| 혼합 | "톡스토어 매출 왜 빠졌지?", "삼치 품절이 매출에 얼마나 영향?" | 숫자 조회 + 글 검색 + 종합 리포트 본문 참조 → 사실/추정 구분 답 |

유형을 사용자가 고르지 않는다. 비서가 질문을 읽고 도구를 고른다.

### 2-2. 도구 (종합 리포트 루프 방식, 최대 8회)
| 도구 | 하는 일 | 안전 |
|---|---|---|
| `run_sql` | 지금의 SELECT 전용·화이트리스트·5,000행 실행 | `validateReportSql` 그대로 |
| `schema` | 질문에 관련된 테이블의 스키마 설명만 돌려줌 | 15KB 카탈로그를 매번 넣지 않아 토큰 절약 |
| `search_text` | 글 본문 검색: VOC 내용·네이버 문의 질문/답변·종합 리포트 본문·월간 VOC 리포트·CS 매뉴얼·생산 요청 메모·변경 기록 메모. 기간·채널·키워드 필터, 결과 최대 30건(각 300자) | 전화번호·이메일은 검색 결과에서 마스킹. `sales_customers`·`bank_deposits`·계정·토큰은 도구에 없음 |
| `read_report` | 종합 리포트(일일·주간·월간) 본문 전문 1건 | 대표 결정 2 |
| `stock_status`·`channel_trend`·`listing_status`·`sku_detail` | 종합 리포트 도구 재사용 | 이미 검증됨 |
| `ads` | 메타·네이버 집계(종합 리포트 사실 수집 함수 재사용, 기간 지정) | 외부 API 지연 → 60초 상한 |

### 2-3. 답의 모양 (화면 고정 틀)
```
답(2~5문장)                                   ← 질문에 바로 답. 숫자는 표기 규율대로
근거
  표 1: 채널별 10월 매출 (SQL 보기 ▸)          ← 조회한 표는 접힌 카드, 펼치면 표 + SQL
  인용 3건: 네이버 문의 10-12 "…", VOC 10-13 "…"  ← 글 근거는 출처·날짜·원문 300자
사실 / 추정                                    ← 데이터가 말하는 것 vs 비서의 해석(종합 리포트 관례)
한계                                           ← 안 본 것, 기간 밖, 데이터 없음
이어서 물어볼 것 3개                           ← 클릭하면 바로 질문
```
- 정량 질문엔 '답' 한 줄 + 표 하나로 끝난다(지금과 같은 밀도). 긴 틀은 혼합·정성 질문에만.
- 저장: 답 전체가 아니라 **SQL 과 질문**을 저장(지금처럼). 정성 답은 저장하지 않는다(다음에 다시 물으면 그때 데이터로).
- 루커 SQL 은 정량 답의 표마다 지금처럼 제공.

### 2-4. 판단의 허용 범위 (지금 '무판단' 규칙을 바꾸는 부분)
- 지금: 원인·추천·전망 **전부 금지**. 바꿀 것: **질문이 이유·평가·추천을 물을 때만** '추정' 칸에 쓴다. 그 외엔 지금처럼 사실만.
- '추정'은 반드시 근거(표·인용)를 가리킨다. 근거 없는 추정은 "데이터에 없습니다"로 답한다. 수치 신뢰도(%)는 쓰지 않는다(디자인 원칙).
- 종합 리포트의 '확인됨/추정' 구분과 같은 말을 쓴다(동사 체인 원칙).

### 2-5. 시간·비용
- 라우트 300초(종합 리포트와 같음), 기한 270초, 조사 최대 8회. 기한이 가까우면 모은 것으로 답하고 "조사를 다 못 했다"고 쓴다.
- Hobby 요금제 300초 한계는 종합 리포트와 같다. 긴 질문이 잘리면 Vercel Pro(800초) — 별도 결정.
- 비용: 질문마다 입력·출력 토큰과 추정 비용 표시(관리자), 월 상한(기본 $60)을 설정에 두고 넘으면 Sonnet 으로 내려 답한다. 기능별 끄기 스위치.
- 캐싱: 시스템 프롬프트·도구 정의는 프롬프트 캐시, 스키마는 도구로 필요할 때만.
- **모델(2026-10-19 대표 확정)**: 조사·최종 답 = Fable 5.1 / 보조 작업(검색 결과 추리기·후속 질문) = Opus 5.5 생각 강도 '낮음'(API 에 'Opus 빠른 버전' 모델은 없어 effort low 로 대신) / 월 상한 초과 시 전체 Opus 5.5 낮음.

### 2-6. 진행 표시
질문 뒤 "조사 중 — 채널별 매출 조회 → 문의 검색(배송) → …" 처럼 도구 호출 로그를 한 줄씩 보여 준다(종합 리포트의 toolLog 재사용). 30초 넘으면 기다릴 이유를 사용자가 안다.

### 2-7. 자리와 이름
- 메뉴: 리포트 › **데이터 비서**(커스텀 리포트를 이름만 바꾼다 — 주소 /report 유지, 저장 리포트 그대로).
- 홈 상단 '가이드 검색' 옆이 아니라 전역 검색(Ctrl+K)에 "비서에게 묻기" 항목 하나 — 검색어를 그대로 질문으로 넘긴다.
- Teams 에서 묻기(2차): 채널에 "@비서 …" → 같은 엔진 → 답을 카드로. 발신은 수동 전환 전까지 보류.

## 3. 안전·개인정보
- 읽기 전용은 그대로(SELECT 전용·화이트리스트·`run_report` SECURITY DEFINER). 도구가 늘어도 **쓰기 도구는 없다**.
- 글 검색 대상에 고객 이름·연락처가 섞일 수 있는 곳: 네이버 문의 본문, VOC 상세. 답에 넣기 전 전화·이메일·주소 패턴 마스킹, 고객 이름은 성만("김**"). 대표 결정 1.
- 대화 기록은 브라우저 세션에만(지금처럼). 서버에 질문 로그는 비용 집계용 최소(질문·토큰·시각·사용자)만 남긴다.

## 5-1. 대화형 (2026-10-19 대표 요청, 1차 이후 추가)
대표: "명확하지 않은 내용은 한번 더 물어보는 챗봇 형태로" → 첫 판(되묻기 1회 한정 도구)은 예시 질문에도 바로 조사해 버려 "아예 처음부터 챗봇처럼 대화" 로 다시 설계.
- 엔진: 매 메시지에 모델이 셋 중 하나 — ① 분명하면 도구 조사 → [최종 답] JSON(`kind:"answer"`), ② 핵심 조건이 비면 조사 전에 **평문** 되묻기(`kind:"chat"`, JSON 없음) — 선택지 버튼을 붙이려면 `ask_user(question, options)` 도구(`kind:"clarify"`), ③ 데이터가 필요 없는 말(인사·설명·계획 확인)엔 평문 짧은 답(`kind:"chat"`).
- 판정(코드): 도구 응답이 없고 이번 턴에 run_sql·search_text·read_report 를 안 돌렸는데 본문이 JSON 이 아니면 chat. 조사한 뒤의 비JSON 은 종전처럼 JSON 재요청. ask_user 는 조사 시작 전에만(아니면 도구 오류로 돌려보내 가정 진행). 되묻기 횟수 제한은 프롬프트로만(같은 요청에 세 번까지, 한 메시지에 두 가지까지).
- 되묻는 기준(프롬프트): 기간 없음·대상 넓음(고객=구매자? 주문?)·지표 뜻 갈림·**비교 기준 없음("빠졌다·늘었다"는 반드시 묻는다)**·묶음 단위. 문맥·오늘 날짜로 정해지는 것과 사소한 차이는 가정 + limits.
- 이력: 최근 8턴(`AskHistoryTurn.kind`). 모델엔 되물음 `[되물음] …`, 조사 답 `[조사 답] …`, 평문은 그대로.
- 화면: 평문 답 = 말풍선 카드(ChatView), 선택지 되물음 = ClarifyView(버튼 → 답 보내기, 답한 뒤 잠금), 조사 답 = 기존 AnswerView. 질문칸은 대화 아래, 직전 턴이 답이 아니면 안내 줄 + [답하기].
- 비용: 평문 턴은 모델 호출 1회(조사 없음)라 질문당 몇 센트. 월 상한 그대로.
