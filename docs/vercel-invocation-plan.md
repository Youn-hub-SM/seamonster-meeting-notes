## 2. 실행 단계

### 1단계 — 사이드바 링크 미리 읽기 끄기 (30분, 코드만)

- `app/AppSidebar.tsx` 의 `<Link>` 6곳, `app/HomeSitemap.tsx`·`app/HomeQuickLaunch.tsx` 에 `prefetch={false}`.
- 대가: 메뉴 클릭 뒤 페이지가 0.1~0.3초 늦게 뜸(지금도 서버 렌더라 체감 차이 작음).
- 화면 안의 본문 링크(발주 목록 등)는 그대로 둔다 — 수가 적고, 미리 읽기가 유용한 자리.
- 배포: dev → 베타 확인 → main.

### 2단계 — 중계 데몬이 Vercel 대신 DB 를 보게 (반나절, 마이그레이션 + 데몬 + 중계 서버 재배포)

목표: 10초 체감은 유지(대표 결정 2026-09-09)하면서 빈 회차의 Vercel 호출을 0 으로.

- migration 157: `channel_commands_pending()` — '대기' 명령이 있는지 true/false 만 돌려주는 security definer 함수, anon 키 RPC 허용. 명령 내용은 노출하지 않는다.
- 데몬: 회차마다 Supabase RPC 로 대기 여부만 확인 → 있을 때만 기존 `?mode=claim` 호출. RPC 실패 시엔 지금처럼 claim 으로 폴백(안전망).
- 중계 서버 `.env.local` 에 `SUPABASE_URL`·`SUPABASE_ANON_KEY` 추가(anon 키는 공개 전제 키라 중계 서버 보관 가능). esbuild 번들 → `bin/channel-commands-runner.cjs` 교체 → 데몬 재기동(워치독이 5분 안에 다시 띄움).
- 원샷 백업 크론 `*/2` → `*/10` (데몬이 죽었을 때의 안전망 역할은 유지, 호출 720 → 144/일).

대안(B 가 부담스러우면): 데몬 주기를 '최근 3분 안에 명령이 있었으면 10초, 아니면 60초' 로. 코드만 고치면 되지만 유휴 뒤 첫 명령이 최대 60초 걸리고, 감축은 85% 선.

### 3단계 — 측정 (배포 3일 뒤)

- Vercel 사용량 화면 › Invocations 카드 › 경로별 상위 목록을 전후 비교. 특히 `/api/channel-commands` 와 `?_rsc=` 붙은 요청.
- 목표: 월 환산 1,000,000 → 400,000 이하.
- 여기서 2번(prefetch) 비중이 작게 나오면 그걸로 끝. 크게 나오면 본문 링크까지 확대.

### 4단계 — 활성 CPU (다음 달 수치 보고 판단)

- 11월 첫 주 사용량에서 Active CPU 가 2시간 이하면 색인이 원인이었던 것으로 종결.
- 여전히 높으면 `ms365` 색인 경로·발주처리 엑셀 파싱·상세 이미지 변환(puppeteer)을 함수별로 본다.

## 3. 하지 않는 것

- 화면 폴링 주기 추가 연장: 이미 손본 상태(60/30/15초, 조건부)라 효과 대비 체감 손해가 큼.
- 외부 웹훅·크론 축소: 월 1만 건 수준이라 의미 없음.
- Pro 전환 결정: 이 계획과 별개. 줄여도 상한의 40% 안팎에서 살게 되므로 화면·리포트가 늘면 다시 닿는다.

## 4. 필요한 확인(대표)

1. 2단계 방식: Supabase 직접 확인(권장, 10초 유지) vs 주기 완화(코드만, 첫 명령 최대 60초).
2. Vercel 사용량 화면의 경로별 상위 목록(또는 브라우저 창 로그인) — 2번 비중과 주기 초기화 날짜 확인용.
