# 파도소리 출고·생산 예상 화면 기획안

- 작성일: 2026-11-20 (매입·생산 분석을 반영해 다시 작성)
- 근거: `docs/factory-shipment-analysis.md` (매입·생산·출고 데이터 분석 보고서)
- 상태: 기획안. 대표 결정(9장) 뒤에 만든다.

## 1. 무엇을 만드는가

pdsr.kr 에 **[예상]** 메뉴를 하나 더한다. 이 화면은 세 가지를 보여준다.

1. **전체 전망** — 다음 3개월 동안 출고, 창고 생산, 매입이 전체로 얼마나 될지.
2. **창고 품목별 생산 권장** — 창고 가공품마다 앞으로 얼마가 빠질지(보통 ~ 많을 때), 지금 재고로 버티는지, 모자라면 얼마를 만들어야 하는지.
3. **주문 생산 부하** — 주문 받은 날 만드는 물량이 요일별로 얼마나 될지.

## 2. 분석에서 정해진 원칙

| 분석 결과 | 화면에 반영하는 방식 |
|---|---|
| 생산은 창고 생산과 주문 생산 두 종류다 | 둘을 나눠 보여준다. 생산 권장은 창고 생산에만 낸다 |
| 주문 생산은 출고와 같은 날 같은 양이다 | 품목별로 예상하지 않고 하루 처리량만 보여준다 |
| 창고 가공품 출고의 57%는 현장으로 다시 나간다 | 창고 품목의 수요를 "창고에서 빠진 양"으로 잡는다. 두 파일을 모두 올린다 |
| 전체 물량은 오차 6~17%로 맞는다 | 전체·어종은 예상치 숫자 하나로 보여준다 |
| 품목별은 오차 70~95%다 | 품목은 "보통 ~ 많을 때" 범위로 보여주고, 생산량은 목표 재고 기준으로 잡는다 |
| 중량 칸이 7~23% 부풀어 있다 | 올린 파일의 중량 칸을 쓰지 않고 수량 × 단위로 다시 계산한다 |
| 주요 순살은 1~3일마다 만든다 | 범위와 목표 재고를 주 단위가 아니라 일 단위로 정할 수 있게 한다 |

## 3. 올린 파일을 읽는 규칙

분석 보고서에서 쓴 규칙을 그대로 툴에 넣는다.

### 3-1. 중량

| 단위 칸 | 중량 |
|---|---|
| `KG` | 수량 |
| `10KG`, `22.5KG` 처럼 숫자 + KG | 수량 × 그 숫자 |
| `C/S`, `박스` 등 그 밖 | 파일에 적힌 중량 |

### 3-2. 흐름 나누기

같은 날·같은 품명·같은 규격·같은 수량인 행끼리 짝을 짓는다.

| 흐름 | 조건 |
|---|---|
| 주문 생산 | 생산 행 중 같은 날 매출 행과 짝이 맞는 것 |
| 창고 생산 | 생산 행 중 짝이 없고 보관처가 적힌 것 |
| 현장 출고(반제품 투입) | 재료 행 중 같은 날 매입 행과 짝이 없고 보관처가 적힌 것. 완제품을 만들려고 창고에서 다시 올리는 반제품이다 |
| 거래처 출고(창고) | 매출 행 중 생산 행과 짝이 없고 보관처가 적힌 것 |
| 거래처 출고(그날 생산) | 매출 행 중 생산 행과 짝이 맞는 것 |
| 매입 | 매입 행 전체 |

- 창고에서 빠진 양 = 현장 출고 + 거래처 출고(창고).
- 품명에 순살·토막·채·살·포·두절 등이 붙으면 가공품, 아니면 원물로 본다. 생산 권장은 가공품에만 낸다.
- 파일에는 완제품·반제품을 나누는 칸이 없다. 그래서 품목마다 창고에서 빠진 양을 "현장으로(반제품 쓰임)"와 "거래처로(완제품 쓰임)"로 나눠 보여준다. 같은 순살이 두 쓰임을 다 갖는 경우가 많아 품목을 한쪽으로 못 박지 않는다.
- 반제품과 완제품은 짝을 지을 수 없다(11-20 대표 확인). 같은 원료가 다른 형태가 되기도 하고 다른 포장이 되기도 한다. 그래서 반제품 수요를 완제품 예상에서 계산하지 않고, 과거에 창고에서 빠진 양 그대로 본다.
- 수산물잔재물은 모든 예상에서 뺀다. 한 줄 3,000kg 이상 거래는 출고 예상과 품목별 계산에서 빼고, 뺀 출고는 화면 아래에 목록으로 보여준다.
- 창고 생산·매입의 전체 합계에는 3,000kg 이상도 넣는다(큰 묶음 매입·생산은 평소 업무다). 다만 계절 지수는 뺀 값으로 만든다(구현하면서 정함 — 빼면 매입 전망이 25% 낮게 나온다).

## 4. 계산 방법

### 4-1. 전체 전망

출고 전체, 창고 생산 전체, 매입 전체를 같은 방식으로 낸다.

1. 최근 3개월 값을 각각 그 달의 계절 지수로 나눠 평소 수준을 구한다.
2. 그 평균에 예상하려는 달의 계절 지수를 곱한다.
3. 계절 지수는 흐름마다 따로, 쌓인 데이터 전체로 매번 다시 계산한다. 출고와 창고 생산은 계절 모양이 다르다.

### 4-2. 창고 품목별 범위

1. 품목마다 최근 12개월 동안 창고에서 빠진 양을 주 단위로 모은다.
2. **보통** = 주별 값의 가운데 값. **많을 때** = 위에서 20% 자리의 값.
3. 두 값에 지금 달의 계절 지수를 곱한다.

### 4-3. 생산 권장량

- **목표 재고** = 기준 일수 동안 "많을 때" 빠지는 양.
- **생산 권장** = 목표 재고 − 현재고. 0보다 작으면 내지 않는다.
- 현재고는 pdsr.kr 재고 화면의 값을 품명으로 묶어 가져온다.
- 기준 일수는 화면에서 바꿀 수 있게 한다. 지금 현장은 재고를 거의 두지 않고 1~3일마다 채우므로, 기본값을 며칠로 둘지는 9장에서 정한다.

### 4-4. 주문 생산 부하

최근 8주의 요일별 주문 생산량 평균과 많은 날 값을 보여준다. 품목으로 쪼개지 않는다.

### 4-5. 몰림 표시

창고 품목이 거래처로 바로 나가는 양 중 1위 거래처가 절반을 넘으면, 품목 옆에 그 거래처 이름과 비중을 붙인다.

## 5. 화면 구성

메뉴 순서: 재고 · 히스토리 · 상품마스터 · **예상**

| 구역 | 내용 |
|---|---|
| 숫자 줄 | 다음 달 출고 예상 · 다음 달 창고 생산 예상 · 다음 달 매입 예상 · 마지막 데이터 날짜 |
| 월별 추이 | 지난 24개월 실적과 앞으로 3개월 예상. [출고] · [창고 생산] · [매입] 을 골라 본다 |
| 창고 품목 표 | 품목 · 쓰임(현장 비중) · 현재고 · 기준 일수 동안 보통 · 많을 때 · 목표 재고 · 생산 권장 · 최근 생산일 · 몰림 거래처 |
| 품목 펼침 | 품목 줄을 누르면 월별 생산·출고 실적과, 빠진 곳(현장·거래처별) 비중 |
| 주문 생산 부하 | 요일별 평균과 많은 날 |
| 지난 예상 확인 | 지난달에 냈을 예상과 실제의 차이(전체·품목) |
| 뺀 거래 | 자동으로 뺀 대량 출고. 중량을 다시 계산한 행은 올릴 때 건수만 보여준다(원본 행을 저장하지 않으므로 목록은 없다) |
| [데이터 올리기] | 출고 파일과 매입·생산 파일을 고르는 버튼 |

- 창고 품목 표는 생산 권장이 큰 순으로 정렬하고, 권장량이 없는 품목은 접어 둔다.
- 꾸준히 빠지는 품목(최근 12개월 중 11개월 이상, 분석 기준 31개)만 표에 올리고 나머지는 합계 한 줄로 둔다.
- 이 화면만 봐서는 다른 서비스가 있다는 것을 알 수 없게 한다. 칸 밑 안내 문구는 넣지 않는다.
- 차트는 기존 공용 차트 부품을 쓰고, 화면 전용 CSS 는 `.fac-fc-*` 로 이름 붙인다.

## 6. 데이터 흐름

### 6-1. 올리기

1. 사용자가 ERP 에서 받은 엑셀 두 개(이번 파일들과 같은 양식)를 고른다.
2. 브라우저가 두 파일을 읽어 3장의 규칙으로 중량을 다시 계산하고 흐름을 나눈다.
3. **일자 × 흐름 × 품명 × 거래처** 단위로 kg 을 합친다. 원본 행(16만 줄)은 서버로 보내지 않는다.
4. "기간, 흐름별 합계 kg, 새 품명 수, 중량이 바뀐 행 수"를 보여주고 [올리기]를 눌러야 저장한다.
5. 서버는 파일에 든 날짜 범위의 기존 기록을 지우고 새로 넣는다. 같은 파일을 다시 올려도 두 번 쌓이지 않는다.

짝짓기 때문에 두 파일은 같은 기간으로 함께 올려야 한다. 하나만 고르면 올리지 못하게 막는다.

### 6-2. 저장 구조

파도소리 번호열에 마이그레이션 하나를 더한다(`supabase/migrations/factory/010_flows.sql`).

| 대상 | 내용 |
|---|---|
| `factory.flows` 표 | 일자 · 흐름 · 품명 · 거래처 · kg · 대량 거래 여부 · 올린 사람 · 올린 시각 |
| `factory.flow_overview()` 함수 | 화면이 쓰는 합계 한 묶음(월 × 흐름, 가공품의 주 × 품명, 1위 거래처, 주문 생산 일별, 대량 거래) |
| `factory.flow_item()` 함수 | 품목 하나의 월별 흐름과 거래처별 출고 |
| `factory.commit_flows()` 함수 | 올리기 마무리 — 같은 기간의 옛 기록 삭제와 새 기록 공개를 한 번에 |
| 설정 값 | 목표 재고 기준 일수, 표에서 뺀 품목(b2b_settings 의 `factory_forecast`) |

- public 스키마는 건드리지 않는다.
- 적용은 대표가 Supabase SQL Editor 에서 한다. 적용 전에도 화면이 죽지 않게 "데이터가 아직 없습니다" 상태로 뜨게 한다.
- 화면은 표를 줄 단위로 읽지 않고 함수 한 번으로 합계를 받는다(뷰를 페이지로 읽는 것보다 호출이 적다).

### 6-3. 품명 잇기

두 파일의 품명과 pdsr.kr 상품마스터의 품목 이름은 `삼치순살`, `고등어순살`처럼 같은 방식으로 적혀 있다. 이름이 같으면 자동으로 잇고, 안 이어진 품목은 현재고 칸을 비운 채 표 아래에 따로 모은다. 실제로 몇 개가 이어지는지는 만들 때 운영 데이터로 확인한다.

## 9. 대표 결정이 필요한 것

### 먼저 확인할 것

분석 보고서 9장의 해석이 실제 업무와 다르면 3장의 규칙부터 바뀐다.

- 보관처가 적힌 생산 = 창고에 넣는 생산, 같은 날 매출과 짝이 맞는 생산 = 주문 생산으로 읽어도 되는지. (창고에서 현장으로 다시 나가는 것이 반제품 투입이라는 점은 11-20 확인됨)
- 원물 상태로 창고에 넣은 것(대구, 새우, 광어 등)도 생산 권장 대상에 넣을지. 지금 안은 가공품만 본다.
- 중량 칸과 수량 × 단위가 다를 때 수량 쪽을 믿어도 되는지.

### 결정할 것

| 번호 | 결정할 것 | 제안 |
|---:|---|---|
| 1 | 목표 재고 기준 일수의 기본값 | 7일. 지금 방식(1~3일마다 채움)보다 넉넉하게 잡고 화면에서 바꿀 수 있게 함 |
| 2 | 데이터를 누가, 얼마나 자주 올릴지 | 주 1회, 관리자 계정. 두 파일을 함께 |
| 3 | [예상] 메뉴를 누가 볼 수 있는지 | 관리자만. 현장 계정에는 메뉴를 숨김 |
| 4 | 창고 품목 표에 올릴 범위 | 꾸준히 빠지는 가공품(분석 기준 31개). 나머지는 합계 한 줄 |
| 5 | 원물 매입 필요량까지 낼지 | 이번에는 매입 전체 전망만. 어종별 수율을 확인받은 뒤 2차로 추가 |
| 6 | 메뉴 이름 | 예상 |

## 10. 이번에 하지 않는 것

- 품목별 원물 필요량. 어종별 수율이 아직 확인되지 않았다.
- 규격별 예상. 규격 표기가 2,900종이라 묶을 수 없다.
- 금액 예상. 월말 정산 행 때문에 금액 합계가 맞지 않는다.
- 거래처 발주 예정을 손으로 넣는 칸. 몰림 표시만 하고, 써 본 뒤 필요하면 추가한다.
