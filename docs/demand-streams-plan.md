작성 2026-09-18 · 대표 결정 10건 확정 · 적대 검증 2회 반영본

## 1. 한 줄 요약

온라인 일반·온라인 프로모션·도매 일반·도매 대량, 네 갈래의 수요를 **주간 제조사 생산요청서 한 장의 숫자 하나**로 합친다. 예측형 둘(온라인 일반·도매 일반)은 판매·발송 원장에서 자동으로 나오고, 확정형 둘(행사·대량)은 사람이 등록한 뒤 **목표일까지 남은 주로 쪼개** 이번 주 몫만 더한다. 이미 시켜둔 물량은 빼고, 도매 대량용으로 잡아둔 재고는 도매 일반 계산에서 제외한다.

화면은 새로 만들지 않는다. 열도 늘리지 않는다. 기존 셀의 괄호와 툴팁, 행 펼침만 늘린다.

## 2. 확정된 결정 10건

| # | 항목 | 결정 |
|---|---|---|
| 1 | 리드타임 | **7일**(설정값도 7). 목표 지평 = 리드타임 7 + 발주 주기 7 = **14일** |
| 2 | 최소 생산 단위 | **없음**. 로트 배수 올림 삭제, 1개 단위 올림만 |
| 3 | 도매 일반 예측 | 월 총량이 **성장 중**이고 SKU 단위로는 듬성듬성 → `max(30일 평균, 90일 평균)` |
| 4 | 발송 시 예약 | 물건이 나간 만큼 **계산에서 예약을 줄인다**. 화면에는 "그중 나감 N" 표시 |
| 5 | 확실도(확정/미확정) | **불필요**. 확정된 발주만 등록하므로 개념 자체를 두지 않는다 |
| 6 | 여유분 상계 | **허용 안 함**. 담당자가 소매에서 직접 옮기고, 옮기는 순간 원장이 바뀌어 반영된다 |
| 7 | 도매 대량/일반 분류 | **담당자가 발주 건마다 판단해 체크**. kg 임계 자동 판정은 쓰지 않는다 |
| 8 | 대량 미등록 경고 | **두지 않는다**. 등록을 챙기는 건 사람이 할 일 |
| 9 | 예약 침범 경고 | **남긴다**. 수식으로만 잠그므로 이것이 유일한 방어 |
| 10 | 대량 체크 단위 | **발주 단위**. 한 발주에 대량·소량이 섞이는 일은 거의 없고, 있어도 감안하고 본다 |

## 3. 네 갈래가 어디로 들어가는가

| 갈래 | 입력 | 시점 | 화면 | 산출 |
|---|---|---|---|---|
| 1. 온라인 일반 | 없음(자동) | 상시 | 판매 원장이 곧 입력 | 소매 목표 − 소매 보유 |
| 2. 온라인 프로모션 | MD | 행사 확정 즉시(3주 전) | 생산 요청 › 프로모션 탭 | 행사 잔여 ÷ 남은 주 |
| 3. 도매 일반 | 없음(자동) | 상시 | 도매 출고 원장이 곧 입력 | 도매 목표 − 도매 보유 |
| 4. 도매 대량 | 영업 | 구두로 확보한 당일(2주 전) | /b2b/orders 헤더 [+ 대량 예약] 또는 생산 요청 › 도매 탭 | 대량 잔여 ÷ 남은 주 |

이행 경로도 갈래마다 다르다.

| 사건 | 주체 | 결과 |
|---|---|---|
| 제조사 입고 | 생산담당자 | 소매 재고 증가, 오는 중 감소 (입고는 소매로만 들어온다) |
| 소매 → 도매·프로모션 이동 + 요청서 배정 | 생산담당자·MD | 예약 증가, 확정형 잔여 감소 |
| B2B 발송 일정 등록 | 영업 | 도매 재고 감소 + 같은 만큼 예약 소진 |
| 요청서 [납품 완료] | MD | 예약 해제 |

주간 요청은 지금 동선 그대로다. 매주 수·목에 재고 목록에서 체크 → [선택 N종 생산 요청] → 새 요청 창. 마감일은 이번 주 요청서 하나로 통일한다.

## 4. 수식

```
이번 주 제조사 요청량(품목별)
  = max(0,  max(0,①) + max(0,②) + max(0,③) + max(0,④)  −  ⑤ )

  ① 온라인 일반 = 소매 목표 − 소매 보유
  ② 도매 일반   = 도매 목표 − 도매 보유
  ③ 행사 몫     = Σ ceil(행사 잔여 ÷ 남은 주)
  ④ 대량 몫     = Σ ceil(대량 잔여 ÷ 남은 주)
  ⑤ 오는 중     = 시한 내 제조사 요청서 잔여 합

  소매 목표 = ceil(소매 하루출고 × 지평) + 캘린더 행사 가산(지평 기준) + 수동 보정
  소매 보유 = 소매 재고 + max(0, 프로모션 풀 − 프로모션 유효 예약)
  도매 목표 = ceil(도매 하루출고 × 지평) + 도매 수동 보정
  도매 보유 = 도매 재고 − 도매 유효 예약            (음수 허용 = 침범 상태)
  지평      = 리드타임(7) + 발주 주기(7) = 14
```

**자르는 규칙이 이 수식의 핵심이다.** 네 항을 각각 0으로 자른 뒤(상계 금지 — 결정 6) 합계에서만 ⑤를 뺀다.

- 소매에 남는 재고로 도매 몫을 메우는 것은 **금지**다. 시스템이 종이 위에서 상계하면 "안 만들어도 된다"고 하는데 물건은 소매에 있어 납품이 펑크난다. 담당자가 실제로 옮겨야 한다.
- 반면 **오는 중은 아직 어느 채널에도 없는 재공**이라 상계 금지의 대상이 아니다. 빼지 않으면 지난주에 시킨 행사·대량 몫을 이번 주에 또 청구한다. 리드타임과 발주 주기가 같은 7일이라 지난주 발주는 항상 재공 상태이므로, 이건 예외가 아니라 매주 일어난다.

### 항 정의

| 항 | 뜻 | 데이터 출처 | 화면 표시명 |
|---|---|---|---|
| 소매 하루출고 | 행사·수동 제외분을 뺀 평상시 일평균 | 최근 30일 소매 출고(B2B 발송·채널이동 제외) − 행사 일할분 − 수동 제외분 (현행 그대로) | 하루출고 |
| 도매 하루출고 | 대량을 뺀 평상시 일평균 | 아래 6절 | 하루출고 |
| 표시 예약 | 임자가 정해진 몫 | max(0, min(배정 누계, 요청수량)) 합 | 현재고 셀 "(예약 420)" |
| 유효 예약 | 표시 예약에서 이미 나간 몫을 뺀 값 — 계산에 쓰는 값 | 아래 5절 | 툴팁 "그중 나감 200" |
| 잔여 | 앞으로 만들 확정형 물량 | max(0, 요청수량 − 배정 누계) | 도매 필요량 / 행사 잔여 |
| 오는 중 | 이미 시켰지만 안 들어온 양(시한 내) | 열린 제조사 요청서 잔여 | "+오는 중 260" |
| 정리 대기 | 시한이 지나 계산에서 빠진 잔여 | 파생(날짜 + 잔여) | 배지 "시한 지남 — 정리" |

**요청수량은 언제나 '예약 + 잔여'로 정확히 둘로 쪼개진다.** 예약은 보유에서 빼고 잔여는 주 단위로 나눠 더하므로, 한 물건이 두 항에 동시에 들어갈 수 없다.

## 5. 도매 대량 예약(B안 — 잠금)

넷째 채널을 만들지 않는다. 물건은 도매 재고에 그대로 두되, **열린 도매 납품 요청서에 배정된 누계를 예약으로 보고 도매 일반 계산에서만 뺀다.**

### 표시 예약

```
표시 예약(요청서 R) = max(0, min(배정 누계 A, 요청수량 Q))
   대상: purpose='도매 납품', status in ('요청','진행중'), 시한 내(아래 해제 3층)
```

`min(A, Q)` 상한이 필요한 이유: 입고 매칭이 초과 배정을 허용하므로 상한이 없으면 예약이 부풀어 도매 보충이 과소해진다.

### 유효 예약 — 출고 행을 한 번만 배분한다

**불변식: Σ(모든 요청서의 소진) ≤ Σ(그 품목 도매 발송 출고).**

```
품목 P 에 대해
  txns = inventory_txns 중 product_id=P, type='출고', channel='도매',
         shipment_id is not null, txn_date ≤ 오늘      (수량은 abs — 출고는 음수 저장)
         정렬: txn_date asc, id asc
  reqs = 위 조건의 열린 도매 납품 요청서 R, 표시 예약 cap_R

  각 출고 t 에 대해:
     후보 = { R : t.txn_date ≥ R.request_date
                  and (R.company_id 가 있으면 t 의 거래처 uuid 와 일치, 없으면 무조건 후보) }
     정렬: 거래처 일치 우선 → 납품예정일 asc → req_no asc
     남은 = abs(t.qty)
     각 후보 R: take = min(남은, cap_R − 이미소진_R)
                이미소진_R += take;  남은 −= take
     남은 > 0 이면 버린다 (도매 일반 출고로 간주 — ② 속도가 이미 그 몫을 본다)

  유효 예약 = Σ max(0, cap_R − 이미소진_R)
```

요청서마다 따로 합을 구하면 **같은 출고가 여러 요청서에서 중복으로 소진된다**(발송 300이 두 요청서에서 각각 300씩 총 600을 지운다). 출고 행 기준으로 한 번만 배분해야 한다.

**거래처 매칭은 uuid 조인으로 한다.** `inventory_txns.shipment_id → shipments.order_id → orders.company_id`. 거래처명 문자열은 쓰지 않는다 — 이름을 바꾸면 이전 출고의 스냅샷이 옛 이름이라 매칭이 통째로 깨지고, 동명 거래처가 있으면 남의 발송이 예약을 소진한다. 이름은 화면 표시 전용이다. 같은 조인을 대량 체크(7절)도 쓰므로 공용 헬퍼로 한 번만 만든다.

### 표시

| 자리 | 표시 |
|---|---|
| 재고 목록 현재고 셀(도매·전체 탭) | `540개  예약 420` — 소매 탭의 "+프로모션 N" 병기와 같은 자리 |
| 예약 일부가 이미 나감 | 같은 툴팁에 `예약 420 · 그중 나감 200 — 완료 처리 필요` |
| 도매 재고 < 유효 예약 | 같은 자리 경고색 + 툴팁 "예약 침범 20" |
| 이동 화면 도매 pill | `도매 540 (예약 420)` |
| 요청서 목록·상세 | `예약 420 · 잔여 280 · 납품 10-07` |

### 침범 경고 (결정 9 — 유지)

문구는 **"이 출고가 예약분을 N 침범합니다" 하나만.** 저장을 막지 않는다.

| 경로 | 구현 |
|---|---|
| B2B 발송 선점 출고 | `app/lib/b2b-shipments.ts` 의 저장 함수 한 곳(발주 등록 폼과 [+ 발송일] 창이 모두 여기를 지난다). 번들은 구성품 단위로 검사. warnings 배열 반환 |
| 재고 목록 출고·조정 모달(채널 도매) | 같은 검사 함수. **응답에 warnings 필드를 새로 달아야 한다 — 지금은 경고를 버린다** |
| 소매↔도매 이동(도매→소매) | 같은 검사 함수. 기존 warnings 표시 재사용 |

검사 함수는 공유하되 전달 경로는 셋 다 다르다.

### 예약 해제 5층

| 층 | 장치 | 동작 |
|---|---|---|
| 1 | 사람이 [납품 완료] | 도매 납품 요청서는 100% 배정돼도 자동 완료되지 않는다(**도매 납품에만** 자동완료 중단) |
| 2 | 도매 발송 출고로 FIFO 소진 | **계산에서만** 감소. 화면에는 "그중 나감 N — 완료 처리 필요"로 남는다 |
| 3 | 납품예정일 + 유예일(기본 7) 경과 | 계산에서 제외 + "납품일 지남 — 완료 처리 필요" 배지 |
| 4 | 요청서 취소·강제 완료 | 즉시 0 |
| 5 | 이동 취소 | 배정이 연쇄 삭제되어 자동 감소 |

프로모션 요청서의 자동 완료는 **끄지 않는다**. 끄면 행사 종료 후 소매 합류 크론이 영구 정지한다. 설정 범위를 `purpose='도매 납품'`에만 건다.

부수 효과: 자동 완료를 끄면 100% 확보된 도매 요청서가 이동 화면 배정 목록에 계속 남는다. 이행률 100% 요청서는 기본 접기로 처리하고, 이동 화면 하단 안내 문구("배정으로 요청서가 100% 채워지면 자동으로 완료되어…")를 교체한다.

## 6. 도매 일반 예측

### 실측 근거 (2026-07~09 도매 출고)

| 월 | SKU 종수 | 출고 건수 | 수량 합계 |
|---|---|---|---|
| 7월 | 7 | 22 | 82 |
| 8월 | 13 | 45 | 1,344 |
| 9월(18일까지) | 23 | 88 | 3,865 |

- **월 총량은 성장 중이다.** 90일 평균만 쓰면 7월의 82가 섞여 현재 수요를 크게 과소평가한다.
- **SKU 단위로는 듬성듬성하다.** 상위 8개 SKU 중 3개월 연속 등장한 것은 3개뿐이다. 30일 창만 쓰면 SKU별로 0으로 꺼진다.
- **한 건이 월 물량의 35~70%를 차지한다.** 9월 대구순살 8건 1,450 중 최대 600(41%), 농어순살 5건 200 중 139(70%), 8월은 SKU마다 1건 400(100%). 이 큰 건들이 곧 대량이다.
- 미래 날짜 출고는 2건 11.5로 무시할 수준이다(9월 합계의 0.3%).

### 채택

```
도매 하루출고 = max( 최근 30일 평균 , 최근 90일 평균 )

  두 평균 모두: [오늘까지] 도매 출고 − 대량 발주분 − 도매 수동 보정
               분모는 각각 30 · 90 고정
```

성장 국면에서는 30일 쪽이 이겨 추세를 따라가고, SKU가 한 달을 거르면 90일 쪽이 이겨 간헐성을 흡수한다. 과잉 쪽으로 기우는 부분은 예약·오는 중 차감이 상쇄한다.

**분모 고정이 필요한 이유**: 현행 속도 함수는 "창 안에서 가장 오래된 출고일 ~ 오늘"을 분모로 쓴다. 듬성듬성한 도매에 그대로 쓰면 창을 넓힌 의미가 정반대로 뒤집힌다. 도매에만 분모를 창 일수로 고정한다(원장 자체가 그보다 짧으면 최초 거래일부터).

**미래 컷**: 도매 속도 조회에 `txn_date ≤ 오늘` 을 건다. 지금은 영향이 0.3%지만 조건 한 줄이고, 발송 일정을 미리 잡기 시작하면 바로 커지는 종류의 오차다. 소매 계산은 손대지 않는다.

**도매 수동 보정 열을 살린다.** 현행 도매 분기는 행사·수동 보정을 통째로 건너뛴다. 요청서 없이 나간 큰 건, 명절, 신규 SKU를 사람이 지울 자리가 도매에는 아예 없다. 소매의 제외 필드와 구분되는 도매 전용 필드를 같은 설정 레코드에 둔다(마이그레이션 불필요). 보정은 두 창 모두 분자 항이고 분모는 각 창의 고정값이다.

### 대량 제외 (결정 7)

담당자가 B2B 발주를 등록·수정할 때 **'대량 발주' 체크 하나**를 켜면, 그 발주에서 나간 발송 출고가 도매 일반 속도에서 통째로 빠진다.

```
도매 일반 출고 = 도매 채널 출고 중
    inventory_txns.shipment_id → shipments.order_id → orders.is_bulk = false 인 것만
    (shipment_id 가 없는 출고 — 수동 출고·엑셀·채널이동 — 은 일반으로 본다)
```

kg 임계 자동 판정을 쓰지 않으므로 중량 환산·임계값·SKU 대 발송 단위·중량 미등록 처리가 전부 필요 없다. 판단 기준이 발주처·품목·물량에 따라 달라지는 현실을 사람이 그대로 반영한다.

한계(수용): 한 발주에 대량과 소량이 섞이면 소량까지 속도에서 빠진다. 대표 확인 결과 그런 발주는 거의 없고, 있어도 감안하고 본다.

**초기 1회 소급 체크 필요**: 지난 90일 발주에는 체크가 없어 속도가 오염된 상태다. 7~9월 발주 155건 중 큰 건 소수만 훑어 체크하면 그때부터 정상 값이 나온다. 4단계 직전에 한다.

## 7. 주간 분배 (확정형 공통)

```
잔여    = max(0, 요청수량 − 배정 누계)
기준일  = 이번 주 요청 기준일(설정, 기본 수요일)          ← '오늘'이 아니다
남은일  = 목표일 − 기준일
남은 주 = max(1, floor((남은일 − 리드타임) ÷ 발주 주기) + 1)
이번 주 몫 = ceil(잔여 ÷ 남은 주)
```

행사와 대량이 같은 함수를 쓴다. 다른 것은 목표일의 의미뿐이다(행사 시작일 / 납품 예정일, 둘 다 요청서의 생산마감일 칸).

**기준일을 앵커로 쓰는 이유**: '오늘'을 쓰면 같은 요청서가 월요일에 보면 남은 주 3, 수요일에 보면 2가 되어 이번 주 몫이 조회 시점에 따라 달라진다.

**리드타임을 빼는 이유**: 이번 주 요청분은 7일 뒤에야 도착한다. 현행 식 `max(1, ceil((남은일+1)/7))` 은 그 사실을 무시해, 납품 2주 전(남은일 14)에 3주로 쪼개고 3분의 1이 항상 납품일 다음 주에 도착한다.

| 남은일 | 현행 식 | 새 식 | 도착 검증 |
|---|---|---|---|
| 7 | 2주(절반 지각) | 1주(전량) | 7일 뒤 도착 = 목표일 |
| 14 | 3주(1/3 지각) | 2주 | 마지막 요청분이 14일차 도착 |
| 21 | 4주(1/4 지각) | 3주 | 21일차 도착 |

### 경계 상황

| 상황 | 처리 |
|---|---|
| 목표일 + 확정형 유효일(기본 14) 지남 | ③④에서 **제외**. 화면에는 '정리 대기'로 남고 브리핑이 센다 |
| 목표일 지남(유효일 이내) | 1주(전량) + "목표일 지남" 경고. 숨기지 않는다 |
| 목표일이 리드타임 안 | 1주 + "긴급 — 리드타임 부족". 이 건만 별도 마감일 요청서로 (마감 통일의 유일한 예외) |
| 목표일 없음(옛 데이터) | 요청일 + 리드타임을 목표일로 본다 |
| 잔여 0 이하 | 항을 만들지 않는다 |
| 소수 수량(kg) | 잔여는 소수 둘째 자리 유지, 이번 주 몫만 올림 |

**확정형 유효일이 없으면 무한 루프가 된다.** 무산되거나 배정을 빠뜨린 요청서가 남은 주 1로 매주 잔여 전량을 다시 청구한다. 제조사 요청서에 담아 입고까지 돼도 배정을 안 하는 한 잔여가 줄지 않아 다음 주에 또 전량을 청구한다.

올림 때문에 주간 몫의 합이 잔여를 넘을 수 있으나(잔여 10, 3주 → 4+4+4), 매주 남은 잔여로 다시 나누므로 총량을 넘지 않는다. 같은 품목에 열린 요청서가 여럿이면 **요청서별로 나눈 뒤 품목 단위로 더한다**(합쳐서 나누면 가까운 납품 건이 묽어진다).

## 8. 오는 중의 시한 3단

```
오는 중 = Σ max(0, 요청수량 − 배정 누계)
   대상: purpose='재고 보충', status in ('요청','진행중')

   A. 마감일 ≥ 오늘                                  → 포함
   B. 마감일 < 오늘 ≤ 마감일 + 오는중 유효일(기본 7)
      → 그 품목에 A 요청서가 하나도 없을 때만 포함
   C. 오늘 > 마감일 + 오는중 유효일                    → 무조건 제외, '정리 대기' 표시
   마감일 없음 → 요청일 + 리드타임
```

C가 없으면 영구 락이 된다. 유령 잔여가 오는 중에 남아 권장을 누르고, 권장이 눌리니 그 품목이 이번 주 요청서에 안 담기고, 그래서 마감 미도래 요청서가 영영 안 생겨 유령이 계속 앉는다.

유령 잔여가 생기는 이유는 입고 매칭 창 규칙 때문이다. 규칙 ①이 초과를 허용하며 전량을 창 안 요청서로 가져가므로, 매주 요청하는 주력 품목에서는 지난주 잔여가 규칙 ②(다른 열린 요청서 잔여 채우기)에 도달하지 못한다. 비주력 품목은 ②가 알아서 청소한다.

## 9. 이중 계산·영구 잔존 차단

| 위험 | 차단 장치 |
|---|---|
| 확정형을 예약과 잔여 양쪽에서 센다 | 요청수량 = 예약 + 잔여 항등식. 같은 스캔에서 두 값을 만들어 시점 어긋남도 없앤다 |
| 대량용으로 이미 시킨 슬라이스를 다음 주에 또 요청 | ⑤ 오는 중을 **합계에서** 차감 |
| 선점 출고가 도매 재고를 빼는데 예약이 남아 보유가 이중으로 깎인다 | 예약 FIFO 소진(5절 2층) |
| 같은 출고가 여러 요청서에서 중복 소진 | 출고 행 1회 배분 + 불변식 Σ소진 ≤ Σ출고 |
| 대량 납품 출고가 도매 속도를 부풀린다 | 발주의 '대량 발주' 체크로 제외. 예약 등록을 깜빡해도 속도는 오염되지 않는다 |
| 미래 날짜 출고가 오늘 속도에 들어간다 | 도매 속도 조회에 `txn_date ≤ 오늘` |
| 같은 행사를 캘린더와 요청서에 둘 다 등록 | **행사 단위 우선순위** — 목표일이 그 행사 기간 안에 드는 열린 프로모션 요청서가 있으면 **그 행사만** 캘린더 가산에서 뺀다. SKU 단위로 0 처리하면 같은 SKU의 다른 행사 가산까지 사라진다 |
| 프로모션 풀을 소매 보유에 통째로 더하면서 행사 몫을 또 요청 | 소매 보유 = 소매 재고 + max(0, 풀 − 프로모션 유효 예약) |
| 프로모션 → 소매 역이동 후 예약만 살아남아 소매 보유를 영구 축소 | 프로모션 유효 예약 = min(표시 예약, 풀 잔량) |
| 대량용 물건을 도매 일반 재고로 센다 | 도매 보유 = 도매 재고 − 유효 예약 |
| 유령 잔여를 오는 중에 넣어 현재고와 이중 계상 | 오는 중 시한 3단 |
| 초과 입고를 오는 중에도 현재고에도 센다 | 잔여에 max(0, ·) 바닥. 초과분은 잔여에 남지 않는다 |
| 무산·방치된 확정형 요청서가 매주 전량 재청구 | 확정형 유효일(기본 14) |
| 같은 구두 건이 영업·MD 양쪽에서 두 번 등록 | 저장 시 같은 거래처 + 납품예정일 ±3일 + 같은 품목의 열린 요청서가 있으면 경고(막지 않음) |
| 용도 컬럼 미적용 환경에서 ⑤가 ③④를 상쇄 | 용도 컬럼이 없으면 예약 0 **이고 오는 중도 0**(기능 전체 off) |
| 배정 중복 삽입으로 예약 과대 | 기존 유니크와 중복 무시 삽입 그대로 사용. 새 코드는 배정을 직접 쓰지 않는다 |

**소매에 여유가 있는데 도매·행사 몫을 또 만드는 문제는 상계가 아니라 '옮기기 제안'으로 막는다**(결정 6). 자세한 것은 10절.

| 미적용 폴백(필수) | `company_id` 없으면 거래처 '-', 예약 소진은 품목 전체 도매 발송 기준. **`is_bulk` 없으면 속도 제외를 하지 않는다**(전건 일반 = 종전 동작) — orders 를 조회하는 **모든 분기**에서 컬럼 오류를 잡아 빼고 재시도해야 하며, 한 분기만 빠뜨리면 그 경로에서 조용히 전건 일반이 된다 |
| 설정 키(마이그레이션 불필요) | `production_cycle_days`(7) · `wholesale_velocity_days_short`(30) · `wholesale_velocity_days_long`(90) · `wholesale_reserve_grace_days`(7) · `inbound_stale_days`(7) · `committed_stale_days`(14) · `production_request_weekday`(3=수) · `wholesale_request_autocomplete`(false, 도매 납품 한정) · `reserve_lock_enabled`(단계 스위치) |
| 신규 파일 | `production-openload.ts`(예약·소진·잔여·오는 중 단일 스캔 + 발송→발주 조인 헬퍼) · `production-wholesale-demand.ts` · `production-weekly.ts`(주간 분배 공용) |
| 복원 | 보류된 1단계 커밋을 되돌린 `fa27fcd` 를 revert → `production-inbound.ts`·발주 주기 설정·표시 복원. 시한 3단을 얹은 뒤 켠다 |
| 원장 | `inventory_txns` 는 전혀 건드리지 않는다. **예약은 원장에 행을 만들지 않는 파생값**이라 운영 구코드가 예약을 몰라도 숫자가 틀어지지 않는다 — 같은 실DB에서 단계별 배포가 가능한 이유다. 정합성 대사도 원장만 보므로 영향 없다 |

리드타임 폴백이 코드에서 10이므로 설정 행이 없거나 조회가 실패하면 지평이 14가 아니라 17이 된다. 설정 화면이 `현재 리드타임 7일 · 발주 주기 7일 (지평 14일)` 을 실제 사용값으로 찍어 확인시킨다.

## 12. 숫자 예시 — 대구순살 500g

오늘 2026-09-23(수 = 요청 기준일). 지평 14일.

| 데이터 | 값 |
|---|---|
| 소매 재고 / 프로모션 풀 / 풀 중 배정된 몫 | 320 / 200 / 160 |
| 소매 하루출고 | 28 |
| 도매 재고 / 도매 표시 예약 / 그중 나간 몫 | 540 / 420 / 0 |
| 도매 90일 출고(오늘까지) / 대량 제외 | 1,980 / 900 |
| 프로모션 요청서 | 요청 600, 배정 160, 행사 시작 10-14 |
| 도매 납품 요청서(대신유통) | 요청 700, 배정 420, 납품 10-07 |
| 제조사 요청서 A | 요청 400, 입고 140 → 잔여 260, 마감 09-25 |
| 제조사 요청서 B | 잔여 120, 마감 09-11(12일 지남) |

| 항 | 계산 | 값 |
|---|---|---|
| ① 온라인 일반 | 목표 ceil(28×14)=392 − 보유 (320 + max(0, 200−160)=40)=360 | **+32** |
| ② 도매 일반 | 하루출고 (1,980−900)÷90=12 → 목표 ceil(12×14)=168 − 보유 (540−420)=120 | **+48** |
| ③ 행사 몫 | 잔여 440, 남은일 21 → 남은 주 max(1, floor((21−7)÷7)+1)=3 → ceil(440÷3) | **+147** |
| ④ 대량 몫 | 잔여 280, 남은일 14 → 남은 주 max(1, floor((14−7)÷7)+1)=2 → ceil(280÷2) | **+140** |
| ⑤ 오는 중 | A 260(마감 미도래). B 120은 마감 + 7일을 지나 조건 C로 제외 | **−260** |
| **합계** | max(0, 32+48+147+140 − 260) | **107** |

화면 툴팁: `온라인 +32 / 도매 +48 / 행사 +147 / 대량 +140 / 오는 중 −260 = 107 · 정리 대기 120`

네 항이 모두 양수라 이 주에는 항별 클램프와 단일 클램프의 값이 같다. 차이는 음수 항이 생기는 주에만 나타난다 — 예를 들어 ①이 −600(소매 여유)이면 단일 클램프는 0이지만 이 수식은 75를 청구하고, 그 600은 담당자가 옮겨야 한다.

**지금 시스템이라면**: 소매 권장 = max(0, ceil(28×10) − (320+200 풀 전액)) = 0. 도매 권장 = 30일 일평균이 대량 900을 포함해 42/일 → 안전 420, 재고 540 → 0. **전체 0, 이번 주에 아무것도 시키지 않는다.** 그런데 10월 7일 납품 280과 10월 14일 행사 440이 기다린다. 다음 주에 720을 한꺼번에 시켜야 하고 제조사 주간 캐파를 넘기면 납품이 펑크난다.

## 13. 사건별 검증표

대량 1건만 추적한다(거래처 A, 요청 200, 납품일 4주 뒤). 도매 일반 출고는 0으로 두고 대량 축만 본다. 도매 시작 재고 300.

| 주 | 사건 | 도매 재고 | 표시 예약 | 유효 예약 | 도매 보유 | 대량 잔여 | 남은 주 | ④ | ⑤ | 순 청구 |
|---|---|---|---|---|---|---|---|---|---|---|
| W1 | 예약 등록(200) | 300 | 0 | 0 | **300** | 200 | 4 | 50 | 0 | 50 |
| W1 | 제조사 요청서 제출(50) | 300 | 0 | 0 | **300** | 200 | — | — | 50 | — |
| W2 | 50 입고 → 이동·배정 50 | 350 | 50 | 50 | **300** | 150 | 3 | 50 | 0 | 50 |
| W3 | 50 입고·배정 | 400 | 100 | 100 | **300** | 100 | 2 | 50 | 0 | 50 |
| W4 | 50 입고·배정 | 450 | 150 | 150 | **300** | 50 | 1 | 50 | 0 | 50 |
| W5 | 50 입고·배정(100%) | 500 | 200 | 200 | **300** | 0 | — | 0 | 0 | 0 |
| W5 | 발송 일정 등록(선점 출고 200) | 300 | 200 | **0** | **300** | 0 | — | 0 | 0 | 정상 |

**불변식 세 가지**
1. 누적 요청 50×4 = 200 = 요청수량. 한 단위도 두 번 청구되지 않았다.
2. 도매 보유는 전 과정에서 300에 머문다 — 발송 뒤에도. 예약 소진 차감이 그 구간을 메운다.
3. 마지막 요청분(W4)이 W5 = 납품일에 도착한다. 주간 분배가 리드타임을 빼기 때문이다.

## 15. 주간 운영 규칙

**순서가 규칙이다: 옮기기 먼저, 요청서 나중.**

1. 수요일 아침 재고 목록을 연다. 상단 배너(판매 기록 반영일·대기 입고·마감 지난 요청서)를 먼저 비운다.
2. '옮기면 해결되는 품목'을 확인하고 이동 화면에서 소매 → 도매·프로모션으로 옮기며 요청서에 **배정한다**. 배정을 빼먹으면 예약이 안 잡혀 다른 거래처가 가져갈 수 있다.
3. 재고 목록으로 돌아와 권장 숫자를 확인한다. 이상하면 셀을 눌러 갈래별 내역을 편다.
4. 체크 → [선택 N종 생산 요청] → 마감일 확인 → 요청서 생성 → 엑셀을 내려받아 제조사에 전달한다.
5. 주중에는 물건이 올 때마다 입고만 기록한다(소매로). 납품이 끝나면 요청서에서 **[납품 완료]** 를 누른다 — 이걸 눌러야 예약이 풀린다.

영업은 대량 발주를 구두로 확보한 당일 /b2b/orders 에서 [+ 대량 예약]으로 등록하고, 실제 발주가 들어오면 그 발주에 **'대량 발주' 체크**를 켠다.

## 16. 위험과 대응

| 위험 | 대응 |
|---|---|
| 지평이 7에서 14로 늘어 첫 주 권장이 크게 튄다 | 설정으로 켜고 끈다. 첫 주는 툴팁에 "이전 기준 N"을 나란히 표시해 한 주 비교한 뒤 확정 |
| 예약 소진이 도매 일반 출고까지 먹어 예약을 조기 해제 | 거래처가 지정된 요청서는 그 거래처 출고만 본다. 조기 해제되면 보유가 커져 생산이 줄지만, 그것은 "물건이 실제로 나갔다"는 사실과 일치하고 침범 경고가 드러낸다 |
| 자동완료를 끄면 도매 요청서가 안 닫히고 쌓인다 | [납품 완료] 버튼 + "그중 나감" 배지 + 납품일 지남 배지 + 브리핑 체크, 그리고 2층 소진·3층 유예가 마지막 그물 |
| 상계를 금지해 이미 소매에 있는 물건을 또 만든다 | **옮기기 제안이 유일한 방어다.** 재고 목록·새 요청 창 양쪽에 띄우고 이동 화면 링크를 붙인다. 주간 루틴을 '옮기기 → 요청서'로 못 박고 브리핑이 센다 |
| 영업이 대량 예약을 등록하지 않으면 그 물량을 아무도 안 만든다 | 대표 결정으로 경고는 두지 않는다. 다만 속도 오염은 '대량 발주' 체크로 따로 막히므로 피해가 '미리 못 만듦' 하나로 한정된다 |
| 하루 판매가 택배 발주처리·판매 엑셀 업로드에 의존 | 판매 반영일 배너. 자동 연동은 이 기획 범위 밖 |
| 시한 제외가 진짜 늦게 오는 물량까지 뺀다 | 제외된 잔여는 사라지지 않고 '정리 대기'로 보이며 브리핑이 센다. 유효일은 설정이다 |
| 대량 제외를 과하게 해 도매 목표가 낮아진다 | 제외 비중이 그 품목 출고의 70%를 넘으면 툴팁에 "대량 제외 비중 높음" 표시 |
| 권장이 항 다섯 개짜리 블랙박스가 된다 | 화면이 문장을 조립하지 않고 **서버가 갈래별 숫자를 내려보낸다.** 툴팁·펼침 문장이 곧 검산식이고, 단계별 배포로 한 번에 한 항씩만 들어간다 |
| 열린 요청서 집계로 재고 목록이 느려진다 | 한 번의 스캔으로 예약·소진·잔여·오는 중을 모두 만든다. 실패 시 "집계 실패" 표시(조용한 0 금지) |
| 베타·운영이 같은 실DB | 예약은 원장에 행을 만들지 않는 파생값이라 구코드가 몰라도 무해. 설정 키도 구코드가 무시한다 |
| 30일 평균이 계속 이겨 수요가 꺾여도 과대 목표가 유지된다 | 두 창 모두 오늘까지라 30일이 먼저 내려온다. 그래도 어긋나면 도매 수동 보정으로 조정 |

## 17. 부록 — 검증에서 잡혀 고친 것

두 차례 적대 검증(에이전트 65 + 41)에서 확정된 결함을 반영한 최종본이다. 주요 교정:

- **오는 중을 소매 항 안에서 빼던 것을 합계 차감으로 바꿨다.** 소매 항이 0으로 잘리면 오는 중이 통째로 소실돼 행사·대량 몫을 매주 재청구했다.
- **예약 소진을 요청서별 합산에서 출고 행 1회 배분으로 바꿨다.** 같은 발송이 여러 요청서에서 중복 소진됐다.
- **거래처 매칭을 이름 문자열에서 uuid 조인으로 바꿨다.** 거래처명을 바꾸면 이전 출고가 매칭에서 전부 빠졌다.
- **B2B 발송이 발송예정일로 도매 재고를 미리 뺀다는 사실**을 설계에 반영했다(예약 소진 2층).
- **확정형 잔여와 오는 중에 시한을 넣었다.** 없으면 무산·방치된 요청서가 매주 전량을 재청구하는 무한 루프가 된다.
- **옮기기 제안을 구현 목록에 넣었다.** 상계 금지의 유일한 보상 장치인데 빠져 있었다.
- 침범 경고의 전달 경로가 세 지점에서 각각 다르고, 출고 모달은 경고를 버리고 있었다.
- `is_bulk` 미적용 폴백을 모든 조회 분기에 넣어야 한다는 점을 명시했다.
