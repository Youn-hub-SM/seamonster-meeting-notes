# 생산 요청서, 비서가 스스로 쓰게 만들기 — 학습·평가 계획안 (2026-10-29)

> 목표(대표): 지금처럼 제조사 제약을 하나씩 가르쳐 가면서, 결국 AI 비서가 정해진 주기에 생산 요청서를 알아서 작성하고 사람은 **확정**만 누르게 한다.
> 이 문서는 "무엇을 어떻게 가르치고, 잘 배웠는지 무엇으로 재며, 언제 자동 작성으로 넘어가는가"를 정한 안이다. 대표 결정이 필요한 항목은 §7.

## 0. 지금 있는 것(출발점)

| 요소 | 상태 | 비고 |
|---|---|---|
| 주간 AI 초안 | 운영 | 수요일 설정 시각에 pg_cron 틱(147)이 `/api/production/requests/draft` 를 불러 **수식**(소매 권장 + 도매 필요량 − 입고 예정)으로 제조사 요청서를 '요청' 상태로 만들고 팀즈에 올린다. Claude 는 검토 메모 3~5줄만(수량은 수식). 행사·도매 대량 몫은 사람이 더한다. |
| 확정 흐름 | 운영(10-29) | 요청 목록의 드롭다운 '확정 필요 ▸ 확정'. 확정된 요청서만 재고 목록 '입고 예정'에 잡힌다. |
| 비서 지식 | 운영 | 셰어포인트 [비서] 페이지가 단일 소스. 10-29 '데이터 해석 기준 › 7. 생산 요청' 절 신설(더 간편한 연어·삼치 주 1회, 연어 주 300kg 분배, 입고 예정=확정만). 업데이트 내역 페이지에 변경 기록. |
| 피드백 | 운영 | 답마다 맞아요/틀려요(+사유). 틀려요 사유는 비서에게 이어 전달돼 고친 답을 받는다. 기록은 관리자 집계용 — 비서가 스스로 읽지는 않는다. |
| 생성 경로 | 코드 | `production-request-create.ts` 가 화면 POST 와 주간 초안의 공용 생성 함수(재시도 키·폴백·알림 포함). 비서 도구로 붙이기 좋은 자리. |

"학습"은 모델을 다시 훈련하는 것이 아니다. **규칙(페이지) + 사례(정답 쌍) + 평가(편차)** 세 겹을 쌓아, 비서가 매주 같은 기준으로 같은 품질의 요청서를 내게 만드는 일이다.

## 1. 가르치는 방법 — 세 겹

### 1-1. 규칙 — [비서] 데이터 해석 기준 › 7. 생산 요청
비서가 턴마다 읽는 유일한 '제약 사전'. 아래 항목이 채워져야 수량 판단이 사람과 같아진다. 지인(생산 담당)이 전달하면 그날 반영하고 업데이트 내역에 한 줄 남긴다.

- 품목별 생산 주기(주 1회만 되는 품목, 격주 품목), 품목 묶음 한도(연어 계열 주 300kg 처럼 **같은 원료를 나눠 쓰는 묶음**과 한도)
- 최소 생산 로트·포장 단위(예: 박스 단위 올림), 리드타임(생산 시작 D+3·마감 D+7·판매 가능 D+8 — 이미 코드 기본값)
- 제조사 휴무·명절 전후 규칙, 원료 입고 요일(생산 가능 요일)
- 수량을 올리거나 내리는 판단 기준(예: 예상소진 7일 미만이면 목표의 1.5배, 행사 전주는 행사 예상 판매량 더하기)
- 하지 말 것(예: 두 품목을 같은 주에 넣지 않기, 한 요청서에 품목 n개 초과 금지)

### 1-2. 사례 — '초안 → 확정본' 정답 쌍
사람이 고친 결과가 곧 정답이다. 매주 자동으로 쌓이게 만든다.

- 주간 초안(수식)·비서 초안·**확정된 최종 요청서** 세 벌을 품목별 수량으로 나란히 저장(새 표 `production_draft_eval`, migration 1건).
- 차이는 "추가·제외·수량 ±"로 분류하고, 확정하는 사람이 드롭다운을 '확정'으로 바꿀 때 **한 줄 사유 입력(선택)** 을 받아 같이 저장(예: "연어 300kg 한도 초과라 삼치로 돌림").
- 사유가 반복되면 규칙(1-1)으로 승격한다. 승격 여부는 대표가 판단(§7 ①).

### 1-3. 평가 — 틀려요 사유와 편차 리포트
- 대화에서 비서가 짠 초안에 '틀려요 + 사유'를 남기면 그 자리에서 고친 답을 받는다(10-29 반영). 사유는 피드백 표에 남는다.
- 매주 확정 뒤 '편차 리포트'(품목별 초안 vs 확정, 수정 사유 모음)를 팀즈 생산 채널에 한 장 올린다. 대표가 이 한 장만 보고 규칙을 보강한다.

## 2. 단계별 일정

| 단계 | 기간 | 하는 일 | 끝나는 조건 |
|---|---|---|---|
| 1. 규칙 채우기 + 대화로 연습 | 이번 주~2주 | 1-1 항목을 지인과 채운다. 매주 수요일 초안이 나온 뒤 비서에게 "이번 주 생산 요청서를 짜 줘"라고 시켜 비서 초안을 받고, 대표가 틀려요 사유로 바로잡는다(대화만, 요청서 생성 없음). | 2주 연속 비서 초안이 규칙 위반 0건 |
| 2. 정답 쌍 쌓기 | 2~4주 차 | `production_draft_eval` 표·확정 사유 입력·편차 리포트 구현. 수식 초안·비서 초안·확정본을 매주 기록. | 편차 지표(§3)가 4주 평균으로 산출됨 |
| 3. 비서가 요청서를 직접 만든다 | 4~6주 차 | 비서 도구 `create_production_request`(쓰기)를 연다. 생성은 **'확정 필요' 상태로만**, 주 1장, 품목·수량 상한, 같은 주 중복 생성 금지. 사람은 드롭다운으로 확정. 수식 초안은 그대로 두고 비서 초안과 나란히 비교. | 3주 연속 "수정 없이 확정" 품목 비율 ≥ 80% |
| 4. 자동 작성 | 안정화 뒤 | 수요일 기존 pg_cron 틱 자리에서 **수식 초안 대신 비서 턴**을 서버에서 실행해 '확정 필요' 요청서를 만들고 팀즈에 "확정 필요" 알림. 사람은 확정만. 새 틱·새 크론 없음(기존 147 틱 재사용). | 4주 연속 지표 충족 → 수식 초안 폐기 결정 |

4단계에서도 사람 확정은 남긴다. 확정 드롭다운이 곧 안전장치다.

## 3. 잘 배웠는지 재는 지표

| 지표 | 정의 | 목표 |
|---|---|---|
| 무수정 확정률 | 확정본에서 수량·구성이 비서 초안과 같은 품목 ÷ 전체 품목 | ≥ 80%(3단계), ≥ 90%(4단계 유지 조건) |
| 수량 편차 | Σ\|확정 − 초안\| ÷ Σ확정 | ≤ 10% |
| 규칙 위반 | 7절 규칙을 어긴 건수(주 1회 품목 중복, 한도 초과 등) | 0 |
| 추가·제외 | 사람이 넣거나 뺀 품목 수 | 주 1개 이하 |
| 비용 | 비서 초안 1장 토큰 비용 | 월 상한 안(현재 기준 1장 $1 안팎 예상 — 1단계에서 실측) |

지표는 편차 리포트에 매주 찍고, 업데이트 내역 페이지에는 '규칙을 바꾼 이유'만 남긴다(숫자는 표에, 이유는 페이지에).

## 4. 결과를 뽑는 방법(각 단계의 산출물)

- **1단계** 비서와의 대화 스레드(초안 + 틀려요 사유 + 고친 답)와 업데이트 내역 페이지의 규칙 추가 행. 대표가 보는 것은 업데이트 내역 한 페이지.
- **2단계** 팀즈 편차 리포트 1장/주 + `production_draft_eval` 표(루커·비서 조회 가능). 비서에게 "지난 4주 내 초안이 어디서 틀렸어?"라고 물으면 이 표로 답하게 한다.
- **3단계** 요청 목록에 '확정 필요' 요청서가 비서 이름(assignee 없음, 작성자 '비서')으로 올라오고, 확정 때 사유가 쌓인다.
- **4단계** 수요일 아침 팀즈에 "비서가 생산 요청서 초안을 올렸습니다 — 확정 필요" 알림, 대표는 드롭다운만.

## 5. 비용·부담(가볍게 유지 원칙)

- 새 크론·새 틱 없음. 4단계도 기존 수요일 틱(147)의 호출 1회를 비서 턴으로 바꾸는 것뿐.
- 비서 턴 주 1회(Fable, 도구 10차례 안) — 1단계에서 실제 비용을 재고 월 상한에 반영.
- 폴링 없음. 편차 리포트는 확정 시점에 한 번 계산해 팀즈로 보낸다.
- 마이그레이션 1건(`production_draft_eval` + 확정 사유 컬럼). 개인정보 없음.

## 6. 위험과 대비

| 위험 | 대비 |
|---|---|
| 규칙이 빠져 과소·과다 생산 | 3단계까지 수식 초안을 나란히 두고 큰 차이(±30%)면 팀즈에 경고. 사람 확정이 마지막 관문. |
| 비서가 같은 주에 두 장 만듦 | 생성 도구에 재시도 키(client_key = 주차) — 같은 주 두 번째는 첫 장을 돌려준다(이미 있는 136 규칙 재사용). |
| 모델 교체로 답이 흔들림 | 지표가 2주 연속 기준 미달이면 자동 작성을 끄고 3단계로 되돌리는 스위치(관리자 › 설정 › 생산·재고). |
| 틀려요 사유가 쌓이지 않음 | 확정 드롭다운에서 수정이 있을 때만 사유 칸을 띄운다(수정 없으면 묻지 않음). |

## 7. 대표 결정 필요

1. 사유의 규칙 승격 — 같은 사유가 **몇 번** 반복되면 7절 규칙으로 올릴지(안: 2회).
2. 정답의 기준 — '확정된 요청서'로 할지, '실제 입고량'까지 볼지(안: 확정본. 입고량은 제조사 사정이 섞여 비서 평가에 부적합).
3. 행사·도매 대량 몫 — 비서 초안에 넣을지(안: 3단계부터 프로모션 요청서를 비서가 읽어 더하되, 지금처럼 요청서 자체는 사람이 만든다).
4. 생성 권한 — 비서 도구로 요청서를 만드는 것을 누구의 대화에서 허용할지(안: 대표·생산 담당 계정만).
5. 자동 작성 전환 조건 — §2 표의 "3주 연속 ≥ 80%"로 할지, 더 보수적으로 갈지.
6. 제약 사전 채우기 담당 — 지인이 직접 [비서] 7절을 편집할지, 대표에게 전달해 반영할지(안: 지인이 편집, 업데이트 내역은 반영한 사람이 적는다).
